================================================================================
 PART A — HOW TO USE THIS FILE
================================================================================

 Every build prompt goes through the same loop. Never skip a step.

   ┌──────────────────────────────────────────────────────────────────┐
   │ 1. START   New session? Paste PART B (Master Context) first.      │
   │ 2. BUILD   Paste the next build prompt (e.g. P04.2).             │
   │ 3. VERIFY  Paste prompt V (Verify). It runs every automated      │
   │            check. Then YOU do the manual checks listed under     │
   │            that build prompt, on a real phone or emulator.       │
   │ 4. ERRORS? Paste prompt F (Fix) with the exact error / screenshot│
   │            description. Then go back to step 3.                  │
   │            Repeat 3 → 4 until everything is green.               │
   │ 5. COMMIT  Commit with the message given under the prompt.       │
   │            Tick the task in BUILD_LOG.md.                        │
   │ 6. NEXT    Move to the next build prompt.                        │
   └──────────────────────────────────────────────────────────────────┘

 Extra rules
 -----------
 • If an error appears in something built EARLIER, stop and paste prompt R
   (Regression). Fix it before continuing. Do not build on a broken base.
 • At the end of every phase, paste prompt PA (Phase Audit), then fix
   anything it finds using F → V.
 • After any prompt that builds a screen, paste prompt DR (Design Review)
   as well, and fix what it finds.
 • If the same error comes back 3 times, paste prompt F with the line
   "THIS IS THE THIRD ATTEMPT — step back, find the root cause, and
   propose a different approach before writing code."
 • Never move on with failing tests, analyzer warnings, or a known
   visual bug. "I'll fix it later" is how apps rot.
 • Commit after every green step so you can always roll back with
   `git checkout <last-green-commit>`.

 "Green" means (see APPENDIX for the full list):
   format clean · analyzer 0 issues · all tests pass · builds for
   Android + Web (+ iOS if you have a Mac) · manual checks pass on the
   device matrix · light + dark mode look right · no overflow at 200% text.

----- COPY FROM HERE -----
You are a senior Flutter engineer and product designer building
"Kitabkhana", a production-quality, private, offline-first home library and
reading tracker for Android, iOS and Web (PWA). Work in the existing repo.
Before writing code, read README.md, docs/ARCHITECTURE.md, docs/DESIGN.md and
BUILD_LOG.md if they exist, and follow them.

PRODUCT
- Answers 3 questions offline: Do I own this book? Where is it? Who has it?
- Features: add books (barcode scan, typed ISBN, title search, manual entry),
  locations, "Don't Buy It Twice" scan check (ISBN + edition + title
  matching, works for books without barcodes), lending/borrowing with
  reminders and WhatsApp/SMS nudges, reading tracker (progress, streaks, pace,
  yearly goal, stats), Snap-a-Quote (OCR on mobile, typed on web),
  backup/restore (.kitab zip, replace or merge), CSV export.
- No accounts, no backend, no analytics. Data stays on the device. The only
  network calls are ISBN/title lookups to Open Library.

STACK
- Flutter (latest stable), Dart 3, Material 3.
- Riverpod 3 with code generation (riverpod_annotation, riverpod_generator,
  riverpod_lint). Disable automatic retry for database providers.
- go_router with StatefulShellRoute (each tab keeps its own stack).
- Drift + drift_flutter (SQLite; WASM on web), FTS5 for search.
- http, mobile_scanner, google_mlkit_text_recognition (mobile only),
  image_picker, flutter_local_notifications + timezone + flutter_timezone,
  url_launcher, share_plus, file_picker, path_provider, archive, csv, intl,
  fl_chart, uuid (v7), crypto, logging. Use the latest stable versions
  that resolve together; never pin to old majors.
- Fonts are BUNDLED as assets (offline-first). Never fetch fonts at runtime.

ARCHITECTURE (strict)
- Layers per feature: presentation → application (use cases) → domain →
  data. Platform services sit underneath. Dependencies only point downward.
- Domain is pure Dart (no Flutter imports).
- UI never touches Drift or HTTP directly. Writes go through use cases.
- Errors: sealed Failure classes + Result<T>. No raw exceptions reach UI.
- Every platform-specific capability is an interface with mobile and web
  implementations, injected with Riverpod (ScannerService, OcrService,
  ReminderService, FileStore, ShareService, PermissionService).
- All tables use UUIDv7 text IDs plus createdAt, updatedAt, deletedAt
  (soft delete) and rev. Multi-row writes run in one transaction.
- Folder layout:
    lib/app/        router, shell, theme, l10n
    lib/core/       result, failure, logger, uuid, clock, rate_limiter
    lib/platform/   <service>/ (interface + mobile + web)
    lib/data/       db/, open_library/, cache/
    lib/features/<feature>/{domain,application,data,presentation}/
    lib/ui/         design system components (K-prefixed widgets)

DESIGN SYSTEM — "Ink & Paper" (must feel calm, warm, premium, bookish)
- Light theme "Paper": background #FBF7F0 (ivory), surface #FFFFFF,
  surface-variant #F3EDE3, ink text #1F1B16, muted text #6B6259,
  outline #E5DDD0, primary #B4532A (terracotta), on-primary #FFFFFF,
  secondary #1F5C5B (peacock teal), success #3E7A4F, warning #B7791F,
  error #B3261E.
- Dark theme "Lamplight": background #15120F, surface #1E1A16,
  surface-variant #2A241E, text #F2EBE1, muted #B3A89A, outline #3A322A,
  primary #E08A5B (warm amber-terracotta), secondary #7FB8B5.
- Typography: display/headlines in "Fraunces" (serif); UI/body in
  "Inter" (sans). Both bundled. Book titles always use Fraunces.
  Scale: display 34/40, headline 26/32, title 20/26, body 16/24,
  label 14/20, caption 12/16. Respect system text scaling up to 200%.
- Spacing on a 4-pt grid: 4, 8, 12, 16, 24, 32, 48. Screen padding 20.
- Radii: cards 20, sheets 28 (top), chips 12, buttons 14, covers 6.
- Elevation: avoid heavy shadows. Use 1px outlines and soft, warm shadows
  (black at 6–10%, blur 16–24). Covers get a subtle spine highlight.
- Motion: 200–300ms, easeOutCubic. Hero transition on covers. Gentle
  stagger (30ms) on list entrance. Respect "reduce motion" settings.
- Icons: Material rounded icons only, 24dp, consistent stroke feel.
- Book covers are the hero of the UI. Missing covers get a generated cover:
  a color from a hash of the title (from a curated muted palette), the
  title in Fraunces and the author in Inter.
- Empty states: short warm copy plus a simple line illustration (built
  with CustomPainter or SVG; no stock images) plus one clear action.
- Haptics: light impact on primary actions, success notification on scan
  match.

ANY-DEVICE RULES (must work well on every phone)
- Layout widths: compact < 600dp (bottom nav, 2-col grid; 3-col at
  >= 400dp), medium 600–1000dp (nav rail, 3–4 cols), expanded > 1000dp
  (rail + two-pane list/detail).
- Must look right on a 320dp-wide small phone, a 360–412dp standard phone,
  a 430dp+ large phone, foldables (inner + outer screen), tablets, and in
  landscape.
- Always respect SafeArea, notches, punch-holes, gesture nav bars and the
  keyboard (no content hidden under it).
- No fixed heights for text containers. No overflow at 200% text scale.
- Minimum tap target 48x48dp. Contrast WCAG AA (4.5:1 text, 3:1 large text
  and UI).
- Android: support the lowest minSdk that all plugins allow, target the
  latest SDK, edge-to-edge enabled. iOS: lowest deployment target all
  plugins allow. Web: Chrome, Safari, Firefox, installable PWA.
- Smooth on low-end Android: lazy lists, small thumbnails, no rebuild
  storms, DB work off the UI thread.

CODING STANDARDS
- Null-safe, immutable models, const constructors where possible.
- All user-facing strings go through l10n (ARB files). No hard-coded UI
  strings, colors, sizes or durations; use theme tokens.
- Every new piece of logic gets unit tests. Every new screen gets at least
  one widget test. Fix the cause of an error, never silence the analyzer.
- Keep files focused (< ~300 lines where reasonable).

HOW TO RESPOND TO EVERY TASK
1. Briefly restate the goal and list the files you will create/change.
2. Write COMPLETE file contents. No "..." placeholders, no TODOs left in
   code unless I ask.
3. Run (or tell me to run): code generation, format, analyze, tests.
4. End with: (a) files changed, (b) commands to verify, (c) the manual
   checks I should do on a device, (d) a suggested commit message,
   (e) a one-line BUILD_LOG.md update.
If anything in my request conflicts with this context, stop and ask.

ownership == borrowed → BorrowedIn; else Owned.
